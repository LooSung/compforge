# Compforge 방법론 — 한국어 개념 가이드

이 문서는 Compforge의 **개념과 프로세스**를 한국어로 설명한다.

> **정본은 영어다.** 실제 에이전트가 읽는 규칙은 `skills/`(영어)에 있다. 이 가이드는 스킬을
> 한 줄씩 번역한 미러가 아니라 **개념 설명**이다 — 미러는 드리프트하지만 개념 가이드는 안정적이다.
> 스킬 본문을 바꿔도 이 문서는 개념이 바뀔 때만 갱신한다.

---

## 1. Compforge가 무엇인가

Compforge는 **TypeScript + React 프론트엔드에 수직 특화된 방법론 + 아키텍처 강제 팩**이다.
범용 코딩 에이전트가 아니라, 그 위에 얹혀 **구조를 기본값으로 만드는 하네스**다.

- 대상 스택: **TypeScript + React** (Vite 또는 Next.js). Vue는 1.x 지원
  범위 밖이며 일정이 약속되지 않았다.
- 고정 범위는 [`support-scope.md`](support-scope.md).
- 푸는 문제: 제약이 없으면 에이전트가 600줄 페이지에 `useState`와 `useEffect` 체인을 쌓는다.
- 핵심 지표는 토큰 절감이 아니라 **아키텍처 위반율**과 **재작업률**이다.

용어 대응: skills = 문법, 하드룰 = 린트, `examples/` = 표준 구현, install·commands = 런타임.

자매 팩: 백엔드는 [OOPforge](https://github.com/LooSung/oopforge).

---

## 2. 워크플로 (코드보다 문서가 먼저)

새 기능 영역이나 큰 화면은 코드로 바로 점프하지 않는다. 각 단계 끝에 **사람 승인**이 있다.

```
Discovery → Design → Delivery Plan → Skeleton → Implement → Test
 (플로우)    (트리/상태)   (범위/순서)     (빈 골격)    (한 기능)     (검증)
```

| 단계 | 산출물 | 하지 말 것 |
|---|---|---|
| Discovery | 용어집, 사용자 플로우, 화면 목록, 열린 질문 | 코드 |
| Design | 컴포넌트 트리, 상태 배치 표, API 계약 | 구현 |
| Delivery Plan | 범위, 계약, 구현 순서, 테스트/릴리스 계획 | 코딩 |
| Skeleton | 기능 폴더, 타입 잡힌 빈 컴포넌트/훅 | 비즈니스 로직 |
| Implement | 한 번에 기능 하나, 훅 먼저 | 여러 개 동시 |
| Test | 훅 / 컴포넌트(DOM) | 테스트 없는 로직 훅 |

작은 작업은 전체 파이프라인을 강제하지 않고 **Craft**가 가장 작은 경로를 고른다.
한 화면을 끝까지 걷는 예시는 [장바구니 워크스루](../guides/cart/README.ko.md)다.

## 3. 공개 커맨드

기본 진입점은 **Craft**다. Refactor와 Consult는 인가 경계가 다를 때만 쓴다.

Claude Code에서는 `/compforge:craft`, `/compforge:refactor`,
`/compforge:consult`. Codex·Cursor에서는 `Use Compforge craft: …`처럼
자연어로 호출한다 (`/` 없이).

Craft는:

1. 요청을 분류해 **가장 작은 실행 경로**를 고른다.
2. 결정이 비어 있으면 심문하지 않고 기본값을 제시한다. 스택은 TypeScript + React 게이트를 거친다.
3. UI 로직 전에 **Component Contract**(트리, 상태 홈, props, 쿼리, 테스트 대상)를 채운다.
4. 구현·테스트 후 프로젝트 규칙을 검증하고 완료 보고를 남긴다.

명시적 Refactor는 동작을 보존한 채 구조만 바꾼다. Consult는 조언·리뷰·문서이며
구현 코드를 바꾸지 않는다. 공개 `test` 커맨드는 없다.

advisory 요청이면 구현하지 않는다.

세션이 바뀌어도 일은 끊기지 않는다. 실행 작업은 `.craft/`에 기록을 남기고, **한 세션은 결정 하나만** 끝낸다. 일이 남으면 에이전트가 묻지 않고 `next-session-prompt.md`를 쓴다. 다음 Craft는 그 파일을 먼저 읽고, 사용자가 지난 작업을 꺼내지 않아도 이어서 할지 한 번 묻는다.

## 4. 원칙 (component-discipline)

프론트 작업 전에 읽는 핵심 원칙. 영어 정본은 `skills/principles/component-discipline.md`.

1. **컴포넌트는 그리고, 훅이 결정한다.**
2. **코드 전에 경계** — 트리, 상태 홈, 서버 데이터가 들어오는 곳.
3. **상태를 만들기 전에 집을 이름 붙인다** — 8단 사다리.
4. **불변성** — 직접 변이 금지.
5. **설정 플래그보다 조합** — `children` 먼저.
6. **버그 수정 전에 실패 테스트.**
7. **추상화 전에 빼라** — 구조 면제는 불변식 + 사용자가 쓴 단어로만.
8. **교훈은 구조로 남긴다** — 테스트·린트·예제.
9. **잘못된 추상화보다 중복** — Rule of Three.
10. **코딩 전에 가정을 드러낸다.**
11. **외과수술식 수정만** — 내가 더 나쁘게 만든 결함은 범위 안.
12. **원인 전에 증거** — 반증 가능한 관찰 하나.
13. **서술 주석 금지** — 이름은 what, 주석은 why.
14. **사람 앞에서는 제품 언어** — Feature/훅/슬라이스 이름은 Contract와 코드에만.

## 5. 작성 전 사다리

만들지 말지를 먼저 정하고, 그다음 상태의 집을 정한다. 위부터 타고 처음 걸리는 단에서 멈춘다.

```
컴포넌트를 쓰기 전에
1. 존재해야 하는가?          -> 아니면 만들지 마라
2. 플랫폼 기능인가?          -> <dialog>, <form>, CSS, URL
3. 프레임워크/이미 깔린 의존성인가?

값을 저장하기 전에
4. 이미 가진 것에서 파생되는가? -> 렌더에서 계산
5. 서버에서 오는가?            -> 쿼리 레이어, useState 금지
6. URL에 속하나?               -> search/route params
7. 멀리 떨어진 노드가 공유하나? -> 조합 먼저, 그다음 context/store
8. 그제야                         -> 로컬 상태, 최소
```

줄 수를 아끼려고 빼면 안 되는 것: 로딩/에러/빈 상태, 접근 가능한 이름, 포커스와 키보드, 입력 검증.

## 6. 하드 룰 요약

측정 가능한 한도. 정본은 `skills/principles/hard-rules.md`.

- 컴포넌트 파일 200줄, 파일당 export 1개, 스킬 200줄.
- `strict` + `any` 금지, 직접 변이 금지.
- 서버 상태는 쿼리 레이어, `useEffect`는 외부 동기화만.
- prop drilling 2단계 초과 금지, 피처 간 직접 import 금지.

대상 프로젝트에는 `compforge init`이 ESLint 존 또는 steiger와 PR 체크를 심는다.
